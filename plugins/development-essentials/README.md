# Development Essentials - Core Development Commands

Development Essentials 提供一组面向日常开发的命令。命令是唯一编排层，专用 agent 是不再委派的叶节点，分别负责扫描、分析、实施或验证；需要拆分时只使用原生 `Task`、`TaskOutput` 和 `SendMessage(to, summary, message)` 协议。

## 命令列表

### 1. `/ask` - 技术咨询

**用途**：针对架构问题和技术决策提供建议，不修改代码。

**流程**：读取对话中引用的设计资料和项目文档，结合系统边界、技术选型、扩展性、可靠性与风险进行分析，最后给出统一的架构建议、取舍理由和后续行动。

**示例**：

```text
/ask "如何设计一个支持百万并发的消息队列系统？"
/ask "微服务架构中应该如何处理分布式事务？"
```

### 2. `/code` - 功能实现

**用途**：实现新功能或特性。

**流程**：命令将目标、验收条件、相关文件和项目上下文交给 `code` agent。实施完成后，命令把改动文件和复现或测试命令交给 `change-verifier`，要求输出 `PASS` 或 `FAIL` 以及实际证据。验证失败时，把证据通过 `SendMessage` 续接给同一个 `code` agent 修正，再重新验证，最多进行两轮修正。

**示例**：

```text
/code "实现 JWT 认证中间件"
/code "添加用户头像上传功能"
```

### 3. `/debug` - 系统调试

**用途**：对复杂故障进行证据驱动的根因分析，并在确认后实施修复。

**流程**：

1. 按故障面拆分任务，并发启动多个 `debug-probe` 进行只读探查。
2. 使用 `TaskOutput` 收集探查结果，将证据交给 `debug` agent 深入复现并分析根因。
3. 将诊断结论交给用户确认；确认后由 `code` agent 实施修复。
4. 使用 `change-verifier` 按目标、验收条件、改动文件和复现或测试命令验证修复。
5. 验证失败时，使用 `SendMessage(to, summary, message)` 将证据续接给原 `code` agent，最多进行两轮修正。

**示例**：

```text
/debug "API 响应时间突然增加十倍"
/debug "生产环境出现内存泄漏"
```

### 4. `/test` - 测试编写与审计

**用途**：发现测试缺口并为指定功能补充测试。

**流程**：按真实模块边界拆分范围，由 `test-author` 自行读取实现和现有测试，审计用户可观察契约的测试缺口，选择高价值缺口后编写并运行相关测试；相互独立且文件不重叠的模块可以并发处理。随后由 `change-verifier` 核实新增测试确实覆盖目标契约并重跑验证。验证失败时，通过 `SendMessage(to, summary, message)` 续接负责该模块的同一个 `test-author`，最多进行两轮修正。

**示例**：

```text
/test "用户认证模块"
/test "支付处理流程"
```

### 5. `/optimize` - 性能优化

**用途**：在可复现的度量协议下定位并改善性能瓶颈。

**流程**：

1. 由 `optimize-profiler` 建立基线，记录可重复执行的测量协议和指标。
2. 将基线和目标交给 `optimize` agent 实施优化；实施 agent 必须运行相关测量或测试命令。
3. 由 `optimize-profiler` 使用相同协议重新测量。
4. 由 `change-verifier` 验证功能回归和验收条件。
5. 指标或验证失败时，通过 `SendMessage` 将证据续接给同一个 `optimize` agent，最多进行两轮修正，然后重新测量和验证。

**示例**：

```text
/optimize "数据库查询性能"
/optimize "将 API 响应时间优化到 200ms 以内"
```

### 6. `/review` - 代码审查

**用途**：对代码进行只读的质量、安全、性能和架构审查。

**流程**：

1. 按文件或内聚代码块拆分范围，并发启动多个 `review-triage` 扫描；每个扫描只输出问题线索、位置、维度和疑似严重度，不深挖、不修改。
2. 使用 `TaskOutput` 收集并去重线索，将每条线索交给 `review-analyst` 核实；分析 agent 读取相关调用方和依赖，确认或驳回线索并给出证据、根因和严重度。
3. 命令汇总已确认问题、被驳回线索、修复建议和按优先级排序的行动计划。审查流程不直接修改代码。

**示例**：

```text
/review "src/auth/middleware.ts"
/review "支付模块代码"
```

### 7. `/bugfix` - Bug 修复

**用途**：定位并修复已知 Bug，并验证修复确实消除了问题。

**流程**：命令将错误描述、日志、相关文件和验收条件交给 `code` agent；`code` 负责复现故障、确认根因、实施最小完整修复并运行相关测试或冒烟命令。随后由 `change-verifier` 使用明确的目标、验收条件、改动文件和复现或测试命令独立验证。验证失败时，使用 `SendMessage(to, summary, message)` 把实际证据续接给原 `code` agent，最多进行两轮修正后再次验证。

**示例**：

```text
/bugfix "登录失败后 session 未清理"
/bugfix "订单状态更新不及时"
```

### 8. `/refactor` - 代码重构

**用途**：在保持外部行为不变的前提下改善代码结构和可维护性。

**流程**：命令将重构目标、范围、约束、外部行为保持要求和相关上下文交给 `code` agent；`code` 核对调用关系和测试基线，分步实施重构并运行相关测试或命令。最后由 `change-verifier` 按行为不变量和验收条件独立验证。验证失败时，通过 `SendMessage(to, summary, message)` 续接同一个 `code` agent，最多进行两轮修正。

**示例**：

```text
/refactor "拆分用户管理模块"
/refactor "改善支付流程的代码结构"
```

### 9. `/docs` - 文档生成

**用途**：为指定代码范围生成或更新 API、用户和开发者文档。

**流程**：命令将范围、受众、格式和项目上下文交给 `docs-writer` agent 一次完成。agent 读取相关实现，生成与现状一致的文档和示例，并按项目约定执行相关检查；命令负责汇总结果，不额外虚构文档内容。

**示例**：

```text
/docs "API 接口文档"
/docs "为认证模块生成开发者文档"
```

### 10. `/think` - 深度分析

**用途**：对复杂技术问题进行只读分析，不实施代码修改。

**流程**：直接基于任务和可读取的项目资料整理假设、证据、备选方案、取舍、结论和后续步骤。不启动其他 agent，不编辑文件，也不输出内部思维过程。

**示例**：

```text
/think "如何设计一个高可用的分布式系统？"
/think "微服务拆分的主要取舍是什么？"
```

### 11. `/enhance-prompt` - 提示词增强

**用途**：将模糊的用户指令改写为清晰、具体、无歧义且可执行的提示词。

**流程**：结合当前对话上下文直接改写指令，修正错误、补足约束，并保留代码块等必要格式。不使用工具，不执行任务。

**输出**：仅输出改写后的提示词，无 wrapper、前言、解释或标记。

**示例**：

```text
/enhance-prompt "帮我做一个登录功能"
/enhance-prompt "优化一下这个 API"
```

## 命令选择指南

| 需求场景 | 推荐命令 | 说明 |
| --- | --- | --- |
| 架构建议或技术决策 | `/ask` | 只读咨询，不修改代码 |
| 实现新功能 | `/code` | 实施后由 change-verifier 验证 |
| 调试复杂故障 | `/debug` | 探查、根因分析、用户确认后修复 |
| 编写或补充测试 | `/test` | 审计缺口、编写测试并验证 |
| 性能瓶颈优化 | `/optimize` | 基线、优化、同协议复测和回归验证 |
| 代码审查 | `/review` | 广度扫描线索，再深度核实 |
| 修复已知 Bug | `/bugfix` | 修复后进行可复现验证 |
| 改善代码结构 | `/refactor` | 分析、实施并验证行为不变 |
| 生成项目文档 | `/docs` | 委托 docs-writer 生成或更新 |
| 复杂问题分析 | `/think` | 只读证据分析，不启动 agent |
| 改写用户指令 | `/enhance-prompt` | 仅输出改写后的提示词 |

## 代理列表

以下列表与 `plugins/development-essentials/agents/` 中保留的十个 development agent 一一对应：

- `code` - 实施功能、Bug 修复和行为保持的重构
- `change-verifier` - 按验收条件执行独立验证，输出 `PASS` 或 `FAIL` 及实际证据
- `debug-probe` - 按故障面进行只读探查
- `debug` - 深入复现并分析调试根因
- `optimize-profiler` - 建立基线和按协议复测性能
- `optimize` - 实施性能优化
- `test-author` - 审计模块测试缺口，编写并运行相关测试
- `docs-writer` - 编写和更新项目文档
- `review-triage` - 广度扫描并产出审查线索
- `review-analyst` - 核实审查线索并评估根因与严重度

## 使用原则

1. 命令是唯一编排层；agent 是不再委派的叶节点，按明确边界承担扫描、分析、实施或验证职责。
2. 使用 `Task` 启动叶节点；并发任务在同一批次发出，后台结果统一用 `TaskOutput` 收集。
3. 验证失败时，将实际证据用 `SendMessage(to, summary, message)` 续接给原实施 agent，而不是重新开始无上下文的任务。
4. 所有写入 agent 都必须自行运行相关测试或命令，并如实报告结果。
5. 只在存在真实的范围、深度、实施或验证边界时拆分任务。
